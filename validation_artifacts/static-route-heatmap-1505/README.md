# Static route-heatmap evidence (issue #1505)

All routes are synthetic, generated by `scripts/validate_route_heatmap.py`.
No personal screenshot, activity data or credentials are included.

Baseline: `dac69530fde27a77fe39d158f929cc2fee1814ce`.
Candidate: `e0570f9d8a9f5b4767148070ad8248c9b8198c31`; production analysis and capture
source are unchanged in `b50eee2` (test-isolation-only follow-up).

Runtimes: Docker `qgis/qgis:3.44.11` and `qgis/qgis:4.2.0`, with the repository's
font image. PNG output only, 1000×650, 96 DPI, north-up, regional/town/detail
cameras, EPSG:32632, neutral background. No basemap/reference fidelity is claimed.
Each camera/runtime has two baseline controls and two candidate renders;
within each role all repeated PNGs are byte-identical. Separate fresh captures
before/after deterministic handle closure also produced identical PNG bytes.

Look for narrow red corridors and distinguishable branches instead of the broad
blue/yellow/orange blur. Values and colour normalization are fixed globally.
Bilinear zoom-in resampling softens pixel edges; physical smoothing width stays
20 m, so corridors occupy more screen space at high magnification.

Cold build: 1.09–1.14 s; warm geometry/hash-verified cache: 0.034–0.042 s for this
30-activity synthetic fixture. These are observations, not real-bulk guarantees.
Raster computation has a higher up-front cost than the old memory-point builder.
See each JSON manifest for timed renders, extents, fingerprints and PNG hashes.

Scoped criteria: C25 route usage (not sample/time density); C23 fixed normalization
with display resampling; C24 tile seams tested separately; C28 PNG/QGIS3+4;
C29 repeated controls and cache timings. C26 complex basemap interaction, C27
accessibility simulation, Windows deployment and PDF output remain unassessed.
